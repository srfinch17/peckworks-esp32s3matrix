# Plan: `fluid2`, a FLIP particle fluid, panel-size independent

Date: 2026-09-01
Status: **v6.1, build-ready.** Three adversarial review rounds applied. Claims verified
against the real toolchain (`xtensa-esp32s3-elf-g++ 14.2.0`, three probe compiles of the
real sketch), the real reference, and the real MCP server.
Source: Matthias Muller, Ten Minute Physics #18 (`tenMinutePhysics/18-flip.html`), MIT.
Goal: **works on the first flash.** Every section below exists because something in it
would otherwise have failed that goal.

## 1. What this is

`anim_liquid.ino` is not a particle simulation. It is a level-set trick: one scalar
potential per cell, a sort to find the 32nd largest value, one spring. Six floats of
state. It can never splash, spray, separate, or leave a droplet behind.

`fluid2` is a FLIP/PIC hybrid. Particles carry the velocity, a staggered MAC grid
enforces incompressibility with a Gauss-Seidel pressure solve, and velocity transfers
particle to grid and back every frame.

A reviewer proposed dropping the grid and pressure solve for a particle-only sim.
Rejected: the request was to port this FLIP implementation. Recorded so it is not
re-litigated mid-build.

## 3. COMPILE-SAFETY RULES (read before writing a line)

This project has no compiler in the review loop, and every failed build costs the user a
round trip. These eleven rules were each measured against the real toolchain. Violating any
one of them fails the build or corrupts behaviour silently.

**R1. Wrap the whole file in a diagnostic push/pop.**
`#pragma GCC diagnostic error` is scoped to the **translation unit**, not the file, which
is the same mechanism that got `#pragma GCC optimize("O2")` deleted in section 8. Measured:
with the pragma unwrapped and warnings raised, the build fails with **9 errors in files
that follow `anim_fluid2.ino`** (`anim_gradient.ino:73` where `PI` is a double macro,
`calibration.ino:48` x4 varargs, `mqtt_publisher.ino:154` and `:163` x3 varargs).

```c
#pragma GCC diagnostic push
#pragma GCC diagnostic error "-Wdouble-promotion"
   ... entire anim_fluid2.ino body ...
#pragma GCC diagnostic pop
```

**R1b. Know that the gate does not fire at the user's current IDE setting.**
`platform.txt:39` is `compiler.warning_flags=-w`, selected by "Compiler warnings: None".
Measured: `-w` **silently defeats the pragma**; a deliberate `f*0.5` compiles clean. To
actually run the gate, set **Compiler warnings = Default for one build**. Otherwise the
`f`-suffix discipline is unenforced and must be done by hand. Do not claim the gate ran
when it did not.

**R1c. The pragma does not catch what v5 claimed it did.** `Arduino.h:190-191` includes
`<cmath>`, so `floor(float)`, `sqrt(float)`, `fabs(float)` resolve to the C++ **float**
overloads. Measured: no diagnostic. The pragma catches bare double *literals* and varargs
promotion, and that is all. The libm-returns-double worry was wrong.

**R2. `min()` and `max()` are `std::` templates here, not macros. This is the number one
predicted compile error for this port.** `Arduino.h:75` says "can't define max()/min()";
`:215-216` do `using std::max; using std::min;`. **Mixed-type arguments do not compile**,
and mixed types are exactly what a JavaScript port produces:

```c
min(floorf(v), nx - 2)          // ERROR: no matching function (float, int)
min((int)floorf(v), nx - 2)     // OK
max(2, (int)roundf(x))          // OK, int/int
max(projMax - projMin, 1e-3f)   // OK, float/float
```

Every `min`/`max` in this file must have both arguments identically typed. `constrain()`
and `sq()` **are** macros and double-evaluate their arguments: never pass anything with a
side effect. `abs`, `round`, `isnan`, `isinf` are `using std::` and safe.

**R3. No `struct` or `enum` declared in `anim_fluid2.ino` may be used as a function
parameter.** Arduino emits every prototype into a block near the top of the generated TU
(measured at generated line ~558), while the file body lands at ~2356. So:

```
line  558:  static void f2Zero(F2Arena& a, int n);   // prototype
line 2356:  struct F2Arena { ... };                  // definition
            error: 'F2Arena' was not declared in this scope
```

The arena design invites this exact mistake. **Pass built-in types only** (`float*`,
`int`) across every fluid2 function boundary. If a struct is genuinely wanted, declare it in
`esp32_matrix_webserver.ino` beside `struct CalibrationProfile` (`:130`); the nearby comment
at `:139-140` about resolving order concerns forward-declared *functions*, not the struct, so
do not cite it as precedent. Same for `FLUID_CELL`/`AIR_CELL`/`SOLID_CELL` if they become an
`enum`: keep them `static const int8_t`.

**R4. `f2` prefix on every file-scope symbol, no exceptions.** Verified by `nm` on the
linked ELF: none of `nx ny h r rows u v s p dt K fill density` currently collides, so
there is no link error today. But **never `#define` any short name**: macros leak
textually into the 17 later files and would break real code (`anim_sound.ino:32` declares
`float dt`, `weather.ino:537` has a parameter `int rows`, `calibration.ino:60-68` uses
locals `r`, `g`, `b`). Use `static const int` / `static float`. Function-**local**
variables inside `anim_fluid2.ino` keep the reference's short names so the port stays
diffable against `flip.html`.

Note `static` at file scope still makes a symbol visible to `api_handlers.ino` later in
the same TU, so `static int f2AchievedFill;` is enough for the response field.

**R5. No default arguments on ported functions.** The reference has
`solveIncompressibility(..., compensateDrift = true)` (`:500`). Arduino's generator emits
the prototype *with* the default and the definition repeats it:
`error: default argument given for parameter 4`. Drop it; `compensateDrift` is a computed
value here anyway (section 4).

**R6. `#include "esp_heap_caps.h"`.** Measured: `heap_caps_malloc` and friends compile
without it today via a transitive path, but the header is guarded and free, and relying on
a transitive include is one core upgrade away from a broken build.

**R7. Align every arena sub-region to 4 bytes.** `heap_caps_malloc` guarantees only the
base pointer's alignment. The layout interleaves `float`, `int8_t` and `uint16_t` regions,
and on Xtensa an unaligned `float*` load raises a LoadStoreAlignment exception (a crash,
not a compile error). After each non-float region: `off = (off + 3) & ~3u;`. At 8x8/K=2
the counts happen to be multiples of 4, so it would work by luck and crash on the first
non-square panel.

**R8. `| 1.0f` not `| 1.0` in the JSON block.** ArduinoJson is **7.4.3**, and `doc[k] | d`
is the correct v7 idiom matching liquid's block at `api_handlers.ino:210-227`. But `| 1.0`
yields a `double`, which is a `-Wdouble-promotion` error inside the guarded region. Note
`api_handlers.ino` sorts **after** `anim_fluid2.ino`, so the param block is inside the
pragma's blast radius if R1's push/pop is skipped.

**R9. Do not change `readAccel()`'s signature.** It has **three** other callers:
`anim_sound.ino:23`, `api_handlers.ino:674` (`/api/accelerometer`), and
`mqtt_publisher.ino:160`. Two of them (`anim_sound`, `api_handlers`) follow `anim_fluid2.ino`
in the TU. Add a **new** `readAccelXY(float&, float&)` and have `readAccel` call it plus the
Z pair.

**Also: the `readAccel` forward declaration v5 called for is unnecessary and its stated
reason was false.** Verified from the generated TU: Arduino auto-prototypes *every* `.ino`
function into a block at generated line ~470-760, before any other file's body
(`readAccel` at generated `:582`, reference parameters handled correctly). A redundant
declaration is legal but the misleading comment must not ship.

**Two more reference constructs that are legal JS and hard C++ errors**, beyond the two
already in section 10: `flip.html:510-512` is a dead loop with an empty body (port it and
you get `-Wunused-variable`, just delete it), and the `var s` / `var d` redefinitions
already listed.

## 4. Dimension independence

**Nothing hardcodes 8.** `MATRIX_W` / `MATRIX_H` (`esp32_matrix_webserver.ino:91-92`) are
the only source of panel size. Most existing `anim_*.ino` files do hardcode 8; this one
does not, deliberately.

`K` is **simulation cells per LED**, 1 or 2.

| Symbol | Definition | 8x8, K=2 |
|---|---|---|
| `f2IW`, `f2IH` | `MATRIX_W*K`, `MATRIX_H*K` | 16, 16 |
| `f2NX`, `f2NY` | `f2IW+2`, `f2IH+2` (incl. solid border) | 18, 18 |
| `f2H` | 1.0f (work in cell units) | 1.0f |
| `f2R` (particle radius) | 0.3f, fixed | 0.3f |
| `f2PInvSpacing` | `1.0f/(2.2f*f2R)` = 1.515152f | |
| `f2PNumX` | `(int)floorf(f2NX * f2PInvSpacing + 1e-4f) + 1` | 28 |
| `f2PNumY` | `(int)floorf(f2NY * f2PInvSpacing + 1e-4f) + 1` | 28 |
| `f2PNumCells` | `f2PNumX * f2PNumY` | 784 |
| gravity magnitude | `3.27f * f2IH` cells/s^2 | 52.3f |
| `iters` default | 30 (reference uses 50) | |

**`f2PNumX` and `f2PNumY` are computed per axis.** They are equal only on a square panel,
and the hash index is `cellNr = xi*f2PNumY + yi`, so collapsing them to one `pNum` breaks
every non-square panel undetectably.

The `1e-4f` epsilon is load-bearing: at 64x64/K=1, `f2NX * f2PInvSpacing` is exactly
100.0, and a `float` `floorf()` of an exact integer can land on 99.

The reference's constructor is **not called**: it computes `fNumX = floor(width/spacing)
+ 1` then silently redefines `h = max(width/fNumX, height/fNumY)`, so asking for 16 cells
yields a 15x15 interior. `seedFluid2()` sets the geometry directly. Deviation 1 in
section 10.

**Gravity on a non-square panel** is calibrated to height (`3.27f * f2IH`), so a 32x8
panel sloshes end-to-end at half the speed it sloshes top-to-bottom. A real wide tank does
exactly that. Alternatives if it reads badly: `3.27f * min(f2IW, f2IH)` or
`3.27f * sqrtf((float)(f2IW*f2IH))`.

### On "eventually every pixel its own fluid particle"

Right instinct, lands at `K=1` on a high-resolution panel. One correction: FLIP needs
about **3 particles per cell** to sample the velocity field without aliasing. At one per
cell the transfer back from the grid is undersampled and reads as jitter. `K=1` on a 64x64
panel gives ~3 particles per LED, all sub-pixel: visually the goal, numerically what the
algorithm needs.

### Gravity direction: the single normative block

This supersedes everything. v5 contained two contradictory versions of this code in
different sections, which would not have compiled.

**All file-scope state for this animation, declared in one place.** Every name is
`f2`-prefixed per R4, including the arena pointers, which section 6 tabulates by their
reference names for diffability but which are declared here:

```c
// Gravity direction, SOLVER frame (+y = UP).
static float f2GXn = 0.0f;
static float f2GYn = -1.0f;   // -1 = DOWN. See the sign note below.
// Geometry and counts
static int   f2NumParticles     = 0;
static int   f2NumFluidCells    = 0;
static int   f2NumInteriorCells = 0;   // f2IW * f2IH, set in seedFluid2()
static bool  f2CompensateDrift  = true;
static int   f2AchievedFill     = 0;
// Depth normalization, from the four tank corners (section 9)
static float f2ProjMin = 0.0f, f2ProjMax = 1.0f;
// Arena pointers, all f2-prefixed: f2U f2V f2DU f2DV f2PrevU f2PrevV f2S
// f2ParticleDensity f2InvSSum f2CellType f2FluidCells f2ParticlePos f2ParticleVel
// f2NumCellParticles f2FirstCellParticle f2CellParticleIds f2Density f2Foam f2DepthAcc
```

**The initial value is `-1.0f`, not `+1.0f`, and this is the one place the frame flip
matters.** `liquid` uses `liquidGX = 0.0f, liquidGY = 1.0f` (`:306-307` and again at
`api_handlers.ino:226`, commented "default down until the IMU reports"), but **liquid's
frame is y-DOWN and this solver's frame is y-UP**. The reference applies
`vel_y += dt * gravity` with `gravity = -9.81` (`flip.html:146`), i.e. the sign lives in
the scalar; here it lives in the direction vector while the magnitude `3.27f * f2IH` is
positive. So copying liquid's `+1.0f` points gravity at the ceiling and the fluid falls
**up** on a flat board, which is checkpoint step (a).

Both halves are required: the initializer **and** a reset in `seedFluid2()`. Without them a
board on a desk never exceeds the dead zone, holds `(0,0)` forever, and the panel shows one
flat colour.

Once per frame (not per substep):

```c
// Accelerometer (g-units, board axes) -> gravity direction (SOLVER frame, y UP).
// x mapping and the -ay sign are liquid's, CALIBRATED ON HARDWARE 2026-06-08.
// y is NEGATED on top of that: the board's +y is down, the solver's +y is up.
float ax, ay;
readAccelXY(ax, ay);                         // R9: new function, Z is not read
float gxRaw = -ay;
float gyRaw = -ax;
float mag   = sqrtf(gxRaw*gxRaw + gyRaw*gyRaw);
if (mag > 0.08f) {                           // liquid's dead zone, on the INSTANTANEOUS magnitude
  f2GXn += (gxRaw/mag - f2GXn) * 0.30f;      // low-pass the normalized direction
  f2GYn += (gyRaw/mag - f2GYn) * 0.30f;
}
// else: hold the last direction (board near flat, in-plane direction is noise)

// Gravity vector handed to integrateParticles, with the user's scale knob applied.
float gMag = 3.27f * (float)f2IH * f2GravityScale;   // f2GravityScale default 1.0f, 0 = zero-g
float gX   = f2GXn * gMag;
float gY   = f2GYn * gMag;
```

> **A v5 idea that was tested and withdrawn.** v5 proposed filtering the *raw* vector and
> normalizing at use, to avoid a normalized lerp passing through the origin on a 180-degree
> flip. Review showed the concern is not real at these rates: a physical flip spans many
> IMU samples (58 Hz) and the direction rotates through the intermediate angles, so the
> filter never collapses. Worse, filtering raw makes `mag` a *filtered* magnitude, so during
> a shake the low-passed vector drops under 0.08 and the direction **freezes**, which is a
> regression against `liquid`. Keep the normalized filter. Recorded so it is not
> reintroduced.

## 5. Fill percent and the level fill line

Default **50%**, range **0 to 100**, no cap.

### The naive version is broken. This is the fix.

Rounding the fill *region* to a whole sim row is necessary and not sufficient. The
reference seeds with `numY = floor((rows - 2r)/dy)`, and that floor throws the remainder
away, so the particles never reach the line. Verified:

| Config | Naive result | Achieved fill |
|---|---|---|
| 8x8 K=2, 50% | surface at LED row **4.59** | 42.6% |
| 8x8 K=1, 50% | surface at LED row **5.19** | **35%** |
| 8x8 K=2, 100% | ~2 sim rows of air remain | 88.3% |

Row 4.59 is three full LED rows plus a half-lit fourth: exactly the ragged result the
requirement exists to prevent.

**Round to the region, then rescale the lattice to span it exactly:**

```c
int rows = (int)roundf((float)f2Fill * 0.01f * (float)f2IH);   // f2Fill = the "fill" param, 0..100
rows = constrain(rows, 0, f2IH);                 // R2: all int, safe macro use
if (rows == 0) { f2NumParticles = 0; f2AchievedFill = 0; return; }   // valid empty tank

const float dx0 = 2.0f * f2R;                    // 0.6f
const float dy0 = 0.8660254f * dx0;              // sqrt(3)/2 * dx
int nX = max(2, (int)roundf(((float)f2IW - dx0) / dx0));   // R2: int/int
int nY = max(2, (int)roundf(((float)rows - dx0) / dy0));
float dxE = ((float)f2IW - dx0) / (float)(nX - 1);         // exact span, not floor
float dyE = ((float)rows - dx0) / (float)(nY - 1);

// Lattice ORIGIN is h + r = 1.3f in cell units, matching flip.html:731.
// Start at r instead and the whole tank seeds inside the solid border.
// ODD ROWS GET ONE FEWER COLUMN. See the stagger note below.
for (int j = 0; j < nY; j++) {
  int   cols = (j & 1) ? (nX - 1) : nX;
  float off  = (j & 1) ? dxE * 0.5f : 0.0f;
  for (int i = 0; i < cols; i++) {
    px = f2H + f2R + dxE * (float)i + off;
    py = f2H + f2R + dyE * (float)j;
  }
}
f2AchievedFill = rows * 100 / f2IH;
```

**The stagger, because two reviewers disagreed and both were wrong.** Even rows span
exactly `[1.3, 16.7]`, which is exactly the wall clamp `(f2NX-1)*h - r`. One reviewer said
offset odd rows by `f2R`, another said by `dxE/2`. **Both overrun**: `+0.3` reaches 17.0 and
`+dxE/2` reaches 16.85, and `handleParticleCollisions` would clamp them onto the wall on
frame 1, piling the odd rows' last column against the edge. Correct hex packing in a bounded
box gives offset rows **one fewer column**, so their last particle sits at
`16.7 - dxE/2 < 16.7`. Particle count becomes
`ceil(nY/2)*nX + floor(nY/2)*(nX-1)`: **357** at 8x8/K=2/50%, **765** at 100%. The arena is
still sized at `nX*nY` (780), which covers it.

Verified across 25/50/75/100% at both `K` values and on a 32x8 panel: **every case lands
within 0.02 LED of the boundary.** 8x8/K=2 at 50% gives 26 x 14 = 364 particles with the
settled surface at LED row **4.011**.

Cost: seeded spacing is 1.03x close-packing (1.12x at `K=1`), so `pushParticlesApart`
barely engages at `K=1`. Acceptable.

The **achieved** percentage is returned in the animation POST response, and is one line in
`docs/API.md` because a documented contract changing without its doc is the rule this repo
enforces.

### 100% fill diverges. It must be made to merely look bad.

The v4 claim that 100% "goes rigid" was wrong, and the hazard it named (divide by zero)
cannot occur at any fill: the minimum of `sx0+sx1+sy0+sy1` over interior cells is 2 at the
corner, so `flip.html:534` never fires.

The real failure: with every interior cell FLUID and all four walls solid, the divergence
field telescopes to zero and the Poisson problem is a consistent all-Neumann system.
`compensateDrift` then subtracts `k*max(compression, 0)` from the right-hand side, and
since `particleRestDensity` is the *mean* density over fluid cells,
`sum of max(d - mean, 0)` is strictly positive. The constraint set becomes **empty**, and
SOR at `overRelaxation = 1.9` on an inconsistent system grows without bound: velocity
blow-up into Inf/NaN every substep, worse with more `iters`.

**Fix, with hysteresis:**

```c
f2CompensateDrift = (f2NumFluidCells < (int)(f2NumInteriorCells * 0.97f));
```

A bare `<` chatters: a cell is FLUID only if a particle lands in it that frame
(`flip.html:402-410`), so near 100% a single particle drifting between cells flips drift
compensation on with one air cell available to absorb the entire term, then off again next
frame. That produces a violent pop or a NaN-and-reseed loop, on the exact uncapped
endpoint decision 15.4 says must degrade to stiff and never diverge. The 3% band settles it.

### Seeding invariants

`particleRestDensity = 0.0f` is the **first line of `seedFluid2()`**. It is measured once
ever, gated on `== 0.0` at `flip.html:348`, and its only clearing site upstream is the
constructor at `:128`, which this design deletes. A stale or `NaN` value makes
`compensateDrift` subtract a phantom term forever, with no error surfaced. Every knob
change and the NaN recovery path route through `seedFluid2()`, which also resets `f2GXn`,
`f2GYn` (section 4).

## 6. Memory: one runtime arena, sized for `K_MAX`

Memory scales as panel area times `K` squared, so static BSS cannot work:

Every row is the **`K_MAX = 2`** allocation, because that is what actually gets allocated
(see the policy below). Earlier drafts tabulated 32x32 and 64x64 at `K=1`, which contradicted
the policy four lines under the table and understated them fourfold.

| Panel | Cells at K=2 | Particles at K=2, 100% | Arena (allocated) |
|---|---|---|---|
| 8x8 | 324 | 780 | **~30.6 kB** |
| 16x16 | 1156 | 3120 | ~115 kB |
| 32x32 | 4356 | 12932 | ~478 kB |
| 64x64 | 16900 | 51302 | ~1.85 MB |

A 64x64 panel at `K_MAX=2` needs 1.85 MB, which fits 2 MB PSRAM only barely and leaves
nothing. **For panels above roughly 32x32, `K_MAX` must drop to 1** (a compile-time
`F2_K_MAX` derived from `MATRIX_W*MATRIX_H`, with the `K` control clamped to it). That keeps
64x64 at ~478 kB and is the honest ceiling: "scales to any panel" means "adapts up to a
declared maximum, and says so at compile time", never "unbounded".

**One arena, sized at `K_MAX = 2` and 100% fill, allocated once on first `fluid2` start,
never freed.** Sizing for the current `K` is wrong: `K` is a live control, so the first
`K=2` POST would overflow a `K=1` arena. Sub-arrays are offsets into it, **each aligned up
to 4 bytes (R7)**; the layout is recomputed on reseed, the allocation is not.

- `heap_caps_malloc(size, MALLOC_CAP_INTERNAL | MALLOC_CAP_8BIT)` **first**. The `8BIT`
  flag is required; `INTERNAL` alone does not guarantee byte addressability.
- Fall back to `MALLOC_CAP_SPIRAM` only when internal will not fit.
- Never freed. Allocate/free per animation switch is the churn behind the frames heap
  crash.

Measured from a real build: static DRAM 102,272 bytes with **225,408 free**. v5's "roughly
120 to 180 kB" was pessimistic. 30 kB fits internal DRAM easily, which is where it must be
(section 8, O7).

**Do not measure this with `ESP.getFreeHeap()`.** `esp_psram_extram_add_to_heap_allocator`
is linked in, so PSRAM is in the default heap and that number includes ~2 MB. Use
`heap_caps_get_free_size(MALLOC_CAP_INTERNAL|MALLOC_CAP_8BIT)`.

### The failure path must return `false`, not send a 503

v5 said "refuse with 503". That is wrong and would black-screen the board on a power
cycle. `applyAnimationBody()` (`api_handlers.ino:148`) is shared by HTTP **and** by the
boot auto-resume (`esp32_matrix_webserver.ino:874-882`), and it does not send HTTP
responses; it returns `bool`. On boot there is no 503, only the existing
`"Auto-resume failed to launch (missing baked asset?); falling back to rainbow."` path.

So: **the allocation and seed check runs before `stopAll()` and returns `false`**, exactly
like the `baked` precedent at `api_handlers.ino:164-171`. `handleAnimation()` turns that
`false` into a 503 for HTTP callers; boot resume turns it into a rainbow fallback. Refuse
after `stopAll()` and a failed resume leaves a dark panel with no fallback.

Note the boot resume runs at the **end** of `setup()`, after WiFi and the web server are
up, so the 30 kB allocation happens at the tightest heap moment of the boot rather than
the loosest. Worth watching at the checkpoint.

> **Side finding, outside this feature's scope:** for the same PSRAM reason, the low-heap
> watchdog near `esp32_matrix_webserver.ino:940`
> (`if (ESP.getFreeHeap() < 14000) ESP.restart();`, comment still says "PSRAM-disabled
> board") can never fire. Dead code. Not fixed here; worth its own issue.

## 7. Index clamping

The reference survives `NaN` positions only because of JavaScript typed-array semantics:
`Math.floor(NaN)` is `NaN` and a typed-array write at index `NaN` is **silently
discarded**. `handleParticleCollisions` does not sanitize either, since every `<` and `>`
against `NaN` is false.

In C++, `(int)floorf(NaN)` is undefined behaviour: a write through an arbitrary offset into
a 30 kB arena, twice per substep.

**Signature is `f2idx(float v, int lo, int hi)` and each site keeps the reference's own
bounds.** A uniform `[0, n-1]` clamp is not a safety fix, it is a silent algorithm change:
at the `transferVelocities` and `updateParticleDensity` sites it would let `x0 = n-1` while
`x1 = n-2`, inverting the bilinear pair and splatting into the solid border.

**Bounds are per axis.** The table names the x bound; the y site at each row takes the
matching `f2PNumY` / `f2NY` / `MATRIX_H` value. Section 4 is explicit that collapsing the
two breaks non-square panels undetectably, and that applies here too.

| Site | `flip.html` | x bound (y takes the `...Y` equivalent) |
|---|---|---|
| `pushParticlesApart` counting pass | 164-166 | `[0, f2PNumX-1]` |
| `pushParticlesApart` fill pass | 186-188 | `[0, f2PNumX-1]` |
| `pushParticlesApart` neighbour walk | 204-209 | **unguarded upstream**, `[0, f2PNumX-1]` |
| `updateParticleDensity` | 331-337 | `x0` free, `x1` capped at `f2NX-2` |
| `transferVelocities` | 426-435 | `min((int)floorf(...), f2NX-2)`, no lower bound upstream |
| `updateParticleColors` | 583-585 | `[1, f2NX-1]` |
| **render splat (new code, built in step 7)** | n/a | `[0, MATRIX_W-1]` |

`f2idx` returns `lo` for `NaN` (test `v != v`). The frame-level `isnan` check stays as a
**diagnostic**: once per frame, test the sum of particle x positions; on `NaN`,
Serial-print the active config loudly and reseed. It reports; the clamps protect.

## 8. Optimization pass

Verified against `xtensa-esp32s3-elf-g++ 14.2.0` and the linked firmware, not reasoned
about.

**O1. `Wire.setClock(400000)` in `initIMU()`, placed AFTER `Wire.begin()`
(`anim_liquid.ino:39`)**. Before it, `begin()` discards the setting. The largest single
win in the plan, and it is one line. `readAccel()` is 6 discrete I2C transactions (burst
reads are broken on this chip revision) at the Arduino default 100 kHz: ~420 to 480 us
each, **~2.5 to 2.9 ms per call**, which is 30 to 40% of the frame budget. The QMI8658C is
rated for 400 kHz Fast Mode. This takes it to ~0.8 ms, **saving ~1.7 ms per frame**, and
speeds up `anim_liquid` and `/api/accelerometer` for free.

**O2. `f` on every float literal**, guarded per R1. JavaScript has one number type, so a
copy-paste port carries `0.5`, `2.0`, `1.0` everywhere, and the **ESP32-S3 has no
double-precision FPU**. Measured: `a*0.5 + 2.0` compiles to four soft-float calls
(`__extendsfdf2`, `__muldf3`, `__adddf3`, `__truncdfsf2`), no FPU instruction emitted.

**O3. Precompute `invSSum` per cell at seed time.** The inner loop divides: `p = -div / s`.
Measured: `__divsf3` is a **30-instruction** ROM routine reached by a windowed `call8`,
never inlined at any `-O` level or with `-ffast-math`: ~35 to 45 cycles, **10 to 30x a
multiply**. `s[]` is written only at setup (`:746`) and in `setObstacle` (`:1041`, `:1047`)
which this port deletes, so it is genuinely invariant between reseeds. `invSSum = 1/(sum)`,
or 0 where the sum is zero, is exactly equivalent to the `continue` at `:534` once `p[]` is
gone. Measured on the real loop: 113 to 79 static instructions.

Numerically `1/s` then multiply is up to 1 ulp off correctly-rounded division. Irrelevant:
Gauss-Seidel is self-correcting and `s` only takes values 1 to 4.

> Landmine: `invSSum` must be recomputed on **every** `s[]` change. As specified there are
> no interior solids, so reseed is the only such event. The day an obstacle is added, this
> breaks silently.

**O4. Walk a compacted fluid-cell list.** The solve scans all interior cells and
`continue`s on `cellType != FLUID_CELL` (`:514-515`), 30 times per substep. `cellType` is
written only in `transferVelocities(toGrid)` (`:399-410`) and never touched by the solve,
so building `fluidCells[]` once per substep is safe and pays back 30x. **Build it i-major,
j-minor**, matching the reference's loop order: Gauss-Seidel is order-dependent and a
different sweep order is a different iteration. The same pass yields `f2NumFluidCells`,
which section 5's `compensateDrift` hysteresis needs.

**O5. Share the particle loop between the density pass and the toGrid transfer, but NOT
the index math.** v5 claimed both compute the identical bilinear index. **False, and
following it would have corrupted the sim.** `updateParticleDensity` offsets by
`(h2, h2)` on both axes (`:331`, `:335`); `transferVelocities` offsets by `(0, h2)` for
`u` and `(h2, 0)` for `v` (`:414-415`, `:429`, `:433`). **Three different stencils**, and
section 7's own table already records those sites as having different clamp conventions.
Splat density half a cell wrong and `particleRestDensity` is measured off,
`compensateDrift` pushes a phantom force forever, and the spray flag whitens the wrong
LEDs. What O5 legitimately shares is the **position load and the outer loop**; all three
stencils and both clamp conventions stay. No measurable time claimed for it.

**O6. Unroll the `component` loop in `transferVelocities`.** The reference selects
`f = component == 0 ? this.u : this.v` (`:416-420`), pointer indirection re-resolved inside
the hottest particle loop. Split into two specialized routines so pointers stay in
registers. Verified equivalent: the `:487-495` restore runs twice and the second pass
overwrites with `prevV` again, so hoisting it to a single post-pass is exact.

**O7. Arena in DRAM when it fits, PSRAM only when it must.** Internal SRAM is 3 to 4x
PSRAM on throughput, and PSRAM random access is 5 to 7x slower than sequential at ~76%
cache hit rate. A Gauss-Seidel sweep at stride `f2NY` floats (72 bytes, larger than the
32-byte cache line) is the bad case, realistically **10 to 20x**.

**O8. `readAccelXY()` once per frame** (R9), not per substep, and not reading Z.

**O9. Explicitly NOT `-ffast-math`.** It permits assuming no `NaN` and no `Inf`, which
would license deleting the section 7 diagnostic.

**O10. Degrade in order** when the budget is blown: reduce `iters`, then drop `K` to 1,
then accept dropped frames. Announce each on Serial.

**O11 (deferred, measure first). A real inverse sqrt in `pushParticlesApart`.** The
bit-hack plus one Newton step replaces ~75 instructions and two windowed calls with ~12
inline, worth ~0.35 ms per substep. Deferred until the checkpoint proves it is needed: it
is the one clever thing in the file.

### Removed, with measured reasons

- **Reciprocal-sqrt as v4 stated it: a no-op.** `1.0f/sqrtf(x)` is still a `sqrtf` call
  plus a `__divsf3` call. `__ieee754_sqrtf` already **ends in `divn.s`**, and GCC emits
  `call8 sqrtf` at `-O2`, `-O2 -fno-math-errno` and `-O2 -ffast-math` alike. There is no
  `sqrt.s` on this target. What it reached for is O11.
- **`#pragma GCC optimize("O2")`: deleted.** It would leak into 17 unrelated files (the
  same TU-scope mechanism as R1), GCC documents the attribute as debugging-only, and
  measured on the real solve loop `-Os` gives **79 instructions vs `-O2`'s 100 and `-O3`'s
  94**. Smaller *and* no slower, because the win came from deleting a divide.
- **Precomputed solid-restore border list: deleted.** v4 also had the set wrong (it is the
  ring **plus** the entire `i=1` column and `j=1` row, the wall faces carrying the
  no-penetration condition, so v4's version would have let fluid creep through walls). Not
  worth fixing: done correctly it saves **~17 us per substep, under 0.3% of the frame**,
  for a second index array, a reseed-invalidation hazard, and correctness that depends on
  there being no interior solids.

Also not doing: `IRAM_ATTR`, fixed-point, red-black Gauss-Seidel.

## 9. Rendering

The translation boundary is in **particle coordinates**, and carries no literal 8:

```c
float sx = (px - 1.0f) / (float)f2IW * (float)MATRIX_W;              // interior starts at cell 1
float sy = ((float)(f2IH + 1) - py) / (float)f2IH * (float)MATRIX_H; // y UP -> y DOWN
```

Verified: interior spans `py in [1.0, 17.0]` mapping to exactly `[0.0, 8.0]`, and at the
particle clamps `[h+r, (n-1)h-r] = [1.3, 16.7]` it gives `sx = 0.150 .. 7.850` and
`sy = 7.850 .. 0.150`. Symmetric, no off-by-one, and the 0.15 inset is the particle radius.

**Splat convention, stated rather than delegated.** v5 left this as "state the convention
and clamp or drop", which is an invention point with a visible cost: at `sx = 0.150` a
pixel-centre convention gives `x0 = -1`, and clamping folds 0.35 of that particle's mass
onto column 0 (a hot rim) while dropping loses it (a dead rim), along the entire bottom row
at rest. Use the **corner convention**, which conserves mass at both walls and needs no
drop rule:

```c
int   x0 = f2idx(sx, 0, MATRIX_W - 1);
int   x1 = min(x0 + 1, MATRIX_W - 1);       // R2: int/int
float tx = sx - (float)x0;
```

Three accumulators, all `NUM_LEDS` floats and all listed in the section 6 arena:
`density`, `foam`, `depthAcc`.

Per frame: zero all three, then for each particle bilinearly splat 1.0 into `f2Density`, the
spray flag into `f2Foam`, and `depth` (below) into `f2DepthAcc`. Then per LED, with an
explicit empty-LED branch rather than a divide (**0/0 is a `NaN` the section 7 diagnostic
does not watch for**, since it only sums particle positions):

```c
if (f2Density[k] < 1e-4f) { setPixel(x, y, CRGB::Black); continue; }
float inv     = 1.0f / f2Density[k];
float depth01 = f2DepthAcc[k] * inv;                       // 0 = surface, 1 = deep
float spray   = f2Foam[k] * inv * (f2FoamGain * 0.1f);     // f2FoamGain = the "foam" param 0..10
CRGB  col     = depthColor(depth01);                       // liquid's gradient / heatToColor path
col.r = qadd8(col.r, (uint8_t)(constrain(spray, 0.0f, 1.0f) * 255.0f));   // and g, b
```

That `f2FoamGain` term is the **Splash** control from section 11. v6 exposed the parameter
and then specified a render that never read it.

The spray flag is the reference's own `relDensity < 0.7` test from `updateParticleColors`
(`:591`), the physical condition for airborne fluid. So `updateParticleColors` is a
**seventh kept method**, reduced to that test alone.

### Depth must be measured in the gravity frame, and against the tank, not the particles

"Darker deeper" computed as screen-y inverts the moment the board does. Compute it by
projecting onto the gravity axis:

```c
float proj  = px * f2GXn + py * f2GYn;
float span  = max(f2ProjMax - f2ProjMin, 1e-3f);      // R2: float/float. Never 0/0.
float depth = constrain((proj - f2ProjMin) / span, 0.0f, 1.0f);
```

The `1e-3f` floor is not optional. `f2GXn`/`f2GYn` are a lerp of unit vectors and are never
renormalized, so their magnitude can shrink during fast rotation and collapse the corner
projections onto each other. A 0/0 here produces a `NaN` that the section 7 diagnostic does
not watch for, since that only sums particle positions.

**`f2ProjMin`/`f2ProjMax` come from projecting the four interior tank corners**, not from
tracking particle extremes. Four dot products per frame instead of N, and it fixes a real
artifact: normalizing against particle extremes means one droplet six cells airborne
expands the span from ~7.4 to ~13.4 and compresses every other particle's depth by 0.55
for that frame, so the whole pool pulses whenever it splashes. `liquid` avoids this by
normalizing against its fixed lattice (`anim_liquid.ino:132`, `:142`). Corner projection
also stays defined at `fill = 0`, where there are no particles at all.

Colour reuses liquid's globals and path (`liquidGradient`, `liquidTopColor`,
`liquidBottomColor`, `heatToColor`): no new colour globals, no duplicated depth lerp.
**The `fluid2` param block must set all three itself, including `liquidGradient`**, or a
warm switch from `liquid` inherits stale state (they are only assigned inside
`if (animationName == "liquid")`). Cold boot is deterministic from their static
initializers; a warm switch is not.

`setPixel()` for bounds checking; floor near-black to true off.

## 9.5 Arbitrary orientation, including fully inverted

Gravity is a vector, all four walls are solid, and `handleParticleCollisions` clamps
symmetrically on all four (`:262-265`). The reference is fully x/y symmetric once the open
top is sealed (section 10), so nothing in the solver has a preferred "down". Rotate the
board 180 degrees and the fluid falls to what is now the bottom. The spray flag is
density-based and orientation-free. The depth gradient is orientation-free by construction
(section 9).

**Board flat, face up or face down:** in-plane gravity is near zero, `mag` falls under the
0.08 dead zone, and the last direction is held, which at cold start is the `(0, 1)` default
from section 4. Face-down flat therefore behaves like face-up flat. Intended: there is no
meaningful in-plane "down" and inventing one would make a resting board drift.

## 11. Control surface

Params ride `POST /api/display/animation { type: "fluid2", ... }` (`docs/API.md:23`), and
persist through NVS auto-resume for free. Verified end to end: `handleAnimation()` stores
the raw body verbatim (`api_handlers.ino:477`), debounce-flushes to NVS key `animbody`
(`esp32_matrix_webserver.ino:949-954`), and boot calls the **same** `applyAnimationBody()`
(`:874-882`), so every param round-trips and `seedFluid2()` runs on replay rather than
resuming an empty tank. Same precedent as `claudesweep`'s `resetClaudeSweep()`.

**`fluid2` ignores `speed`, deliberately, and that must be said out loud.** It is a
fixed-timestep simulation: `dt` is always `1/60`, and the frame interval determines how much
real time each rendered frame covers, not how fast the fluid moves. The shared path sets
`animationSpeed` from `speed` at `api_handlers.ino:172`, and the MCP layer rescales 1-5 to
`{150, 100, 66, 40, 20}` ms, so an MCP caller could hand us a 150 ms frame and get
nine-times slow motion. So:

```c
animationSpeed = min(animationSpeed, (uint32_t)33);    // R2: both uint32_t
```

This mirrors the existing frostbite clamp at `esp32_matrix_webserver.ino:962` and avoids
touching the `effectiveRate` chain, since `effectiveRate == animationSpeed` for anything
that is not `rainbow` or `frostbite`.

**The honest consequence:** MCP speeds 1 through 4 all collapse to 33 ms; only speed 5
(20 ms) is distinguishable. The clamp does not extend the speed scale, it discards most of
it, on purpose. `speed` is therefore absent from the control table below, and the studio's
tool description should say `fluid2` runs at a fixed rate.

**Sim time versus wall time, since it decides whether it looks right.** `dt = 1/60` per
substep. At the 33 ms frame interval, **2 substeps advance 33.3 ms of sim time per 33 ms of
wall clock, i.e. real time**; 1 substep advances 16.7 ms, i.e. **half speed**. `substeps`
therefore defaults to **2**, and dropping it to 1 is both the cheapest performance lever and
a deliberate slow-motion look, which on 64 pixels may well be the better one. Nothing scales
`dt` to the measured interval: a variable `dt` into a pressure solve is how these diverge.

### MCP reachability: verified, currently BLOCKED, and cheap to unblock

Read from `claude-expression-studio/mcp_server/index.ts`:

1. **`type` is a closed `enum`** (`:382-392`), 25 names, no `fluid2`. Rejected before any
   HTTP call. **No firmware-side workaround exists.**
2. **Params are an explicit property whitelist** (`:397-427`). The handler is permissive
   (`const payload = {...args}` at `:645`), but Claude only sends declared properties.
3. **`speed` is silently rescaled** (`:654-658`): 1-5 to `{150, 100, 66, 40, 20}` ms. Hence
   the clamp above.
4. **There is no `gradient` property** in the whitelist, and `top`/`bottom` are read only
   inside `if (liquidGradient)` (`api_handlers.ino:218-221`). So a `fluid2` block copying
   that gate would **discard every colour an MCP caller sends** and still report success.

**Firmware-side aliasing, which shrinks the studio PR to almost nothing.** Two of the three
things the user wants controllable already exist in that schema:

|---|---|---|

Both get thicker as the number rises, which is all a user needs; do not assume a shared

**What MCP still cannot reach after the studio PR:** `gradient`, `foam`, `gravity_scale`,

**Viscosity is `flipRatio`, and that is not a fudge.** FLIP has no viscosity term, but
`flipRatio` is the physical dial: 1.0 keeps all particle energy (thin, splashy); 0.0
resamples from the grid every step and is heavily damped (thick, syrupy). The damping FLIP
was invented to avoid is exactly what gives viscosity for free. Slider left-low right-high
onto `flipRatio` **descending**: `flipRatio = 1.0f - 0.35f * viscosity01`. Below ~0.6 it
washes into mush; not exposed.

| `transferVelocities`, both directions and components | 0.58 ms |
| `updateParticleDensity` | 0.09 ms |
| `integrateParticles` + wall collisions | 0.08 ms |
| **Solver subtotal** | **~2.4 ms** |

Plus once per frame: render splat and colour ~0.09 ms, `readAccelXY()` **~0.6 ms after O1
and O8** (2.5 ms without), `FastLED.show()` **~2.2 ms**.

- **1 substep: ~5.3 ms/frame**
- **2 substeps: ~7.7 ms/frame**
- **Worst case** (100% fill, 780 particles, 256 fluid cells, 2 substeps): ~11 to 12 ms

Comfortable against 33 ms. Likely better still: this build links **FastLED 3.10.3** on the
RMT5 driver, whose `show()` waits on the *previous* transmission, so that 2.2 ms overlaps
the next frame's solver work. Do not budget on the overlap.

**Instrumentation brackets the whole frame, not the step.** v4 would have measured the
2.4 ms solver and reported success while the frame cost 7 ms, because `readAccel` and
`FastLED.show()` together exceed the entire optimized solver. Accumulate `micros()` around
the full frame, report the solver as a sub-total, Serial-print mean and worst case every
5 seconds. Scaffolding, removed before the PR.

**The recovery path must survive its own failure.** `effectiveRate` is a floor on the
interval, not a ceiling on step cost: an 80 ms step becomes 80 ms of HTTP latency. So test
configs are posted with **`transient:true`** and the O10 degrade ladder announces itself on
Serial.

   Standalone, benefits `liquid` immediately.

5. Port the seven kept methods in reference order under the compile-safety rules, applying
   `f2idx()` at the **first six** sites with per-site bounds (the seventh is the render

   dropping the default argument and the dead loop, and applying O2 and O4 to O6:
   `integrateParticles`, `pushParticlesApart`, `handleParticleCollisions` (walls only),
   `transferVelocities`, `updateParticleDensity`, `solveIncompressibility` (with the
   `compensateDrift` hysteresis), `updateParticleColors` (spray flag only).

   diagnostic, whole-frame timing, degrade ladder (O10).

    particles over 32 fluid cells (**2.63** per cell, not the 2.25 an earlier draft claimed),

    section 4**, so density is not the tiebreaker it was presented as. `K=2` is still the
    right checkpoint config for a different and better reason: four times the cells means the
    pressure solve resolves a surface at all on a 64-pixel panel, and the first flash should
    test the configuration meant to ship. If either reads as jitter, raising `fill` raises
    the density directly. Flash both steps

    a) at rest, the surface is a flat line at exactly 4 LED rows;

## 15. Decisions (settled)

1. **Idle rotation: no.** `idle_engine.ino` untouched.
2. **Name: `fluid2`.** Locked: animation name, URL, API `type`, NVS resume string.
3. **Licence: MIT, whole repo.** Done.
4. **Fill snaps to sim rows**, default 50%, **no maximum**; 100% degrades to stiff, never
   to divergence.
5. **Panel-size independent** via `MATRIX_W`/`MATRIX_H` and `K`; one runtime arena sized at
   `K_MAX`.
6. **Rich control page** with a live framebuffer preview; params ride the animation POST so
   MCP drives them once the studio PR lands.
7. **Gravity on non-square panels** calibrated to height (`3.27f * f2IH`) by default.
8. **Icon: `⛲`.**
